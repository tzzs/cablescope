# 优化路线图（对标 whatcable）

> 2026-09-13 定稿。背景：对标 [whatcable](https://github.com/darrylmorley/whatcable)（macOS USB-C 检测工具）后的差距分析与优化计划；产品决策为**全量开源、无付费版、双渠道分发**。

## 一、产品与分发模型（定稿）

- **不做付费版**：全功能开源（License 选 MIT/Apache-2.0，避开 GPL×MAS 不兼容红线），可持续性走可选捐赠。
- **双渠道同一代码库**：差异只来自 Apple 硬规则，不人为阉割——
  - **外部版**（主渠道）：全功能含 CLI；Homebrew（cask 装 App + formula 装 CLI）/ GitHub Releases notarized DMG；更新用 Sparkle 或 brew。
  - **商店版**（可选、低优先）：MAS 上架，受规则自然受限——不带 CLI（Guideline 2.4.5）、必须 App Sandbox。Gate A 已验证 AppleHPM 读取 sandbox 可用，端口层数据双版本通用。
- 评级引擎、功率历史、插拔通知等功能**不做任何版本/付费门控**。

### M9 英文本地化修复 + 常驻开销优化 ✅（2026-09-18）

M8 的审查继续往运行时和构建产物里挖，找到两个此前没被任何测试或 CI 步骤覆盖的真问题：

- 🔴 **英文本地化在 CI/发布构建下完全失效（已修）**：与 5401f72 修的 CableKit 问题**同一根因、只修了一半**——经典 SwiftPM `native` 构建引擎（CI 与 release workflow 在用）不编译 `.xcstrings`，只把原始 JSON 原样拷进资源包，`en.lproj` 永不产出。CableKit 当时迁到了经典 `.strings`，但 `Sources/CableScopeApp/Resources/Localizable.xcstrings`（132 条，翻译本身是完整的）没跟着迁。实测确认：`swift build --build-system native` 下 App 资源包里只有 `Localizable.xcstrings`、没有 `en.lproj`。后果链条是全静默的——`bundle_app.sh` 平铺 `*.lproj` 的循环开了 `nullglob`，没有 lproj 就跳过且不报错 → `.app` 里没有任何英文资源 → SwiftUI `Text` 与 `AppLocalization` 双双回退中文 key → **英文用户拿到全中文界面**，而打包"成功"。CableKit 当年是靠 `DiagnosticsTests` 的英文断言暴露的，App 层没有对应断言所以漏了。
  - 修复：132 条译文迁到 `Resources/en.lproj/Localizable.strings`，删除 `.xcstrings`；新增 `AppLocalizationTests` 做断言式回归（英文查表必须返回译文而非中文 key、模板必须保留 `%@` 占位符）。
  - 顺带修 `AppLocalization.resourceBundle()` 的探测顺序：原先"`Bundle.main.localizations` 非空就用 `Bundle.main`"在 `swift test` 下恒真（`Bundle.main` 是 xctest 运行器，自带 en.lproj），查表必然落空——本地化回归测试因此根本测不到真资源包。改为先探测嵌套 `CableScope_CableScopeApp.bundle`（含 CableKit 在 9c60992 补的 .xctest 同级候选路径），`Bundle.main` 兜底。
  - 同类小 bug：`ThroughputSectionView.speedText` 的"无有效数据"回退文案是作为 `%@` 插进 `LocalizedStringKey` 的，插进去的字符串不会再被查表，英文界面显示成 "Write 无有效数据"（译文表里其实有 "No valid data"）。改为显式走 `AppLocalization`。
  - 验证：`swift test --build-system native` 全量 241 用例通过（这是关键验证环境）；`bundle_app.sh release` 实测打印"已平铺语言目录：en.lproj"，`.app` 内 `Contents/Resources/en.lproj/Localizable.strings` 落位正确。

- 🟠 **常驻 CPU 开销优化（实测 -87%）**：`DisplayService` / `ThunderboltService` 每轮快照都重启 `system_profiler` 子进程且无缓存（实测 SPDisplaysDataType ~0.15s、SPThunderboltDataType ~0.05s），而 `CableMonitor` 按 1.5s 兜底轮询重采样——菜单栏 App 常驻运行时实测 `watch` 20 秒累计 CPU（含子进程）**user 1.22 + sys 1.93 = 3.15s ≈ 单核 15.7%**，一天约 11.5 万次子进程启动。
  - 关键观察：兜底轮询间隔只影响显示器/雷雳拓扑的发现延迟，**不影响插拔通知延迟**（插拔走 IOKit 通知桥，近零延迟）——成本最高的两个数据源被绑在了为最快数据源设定的节奏上。
  - 修复：新增 `Services/TTLCache.swift`（"便宜的变化探针 + TTL 上限"，纯逻辑、注入时钟、6 个单测覆盖 key 变化/过期/并发去重）。`DisplayService` 拿在线显示器 ID 集合当 key（纯 CG 调用无子进程，插拔立即失效，30s TTL 只作分辨率切换之类"key 看不见的变化"的兜底）；`ThunderboltService` 无同等便宜可靠的变化探针（雷雳 IORegistry 节点的插拔行为未在真机验证），key 恒定退化为纯 TTL（5s），代价是新接入雷雳设备最多延迟 5s 出现，已如实写进两份 README 的已知限制。
  - 实测效果：同样的 20 秒 `watch`，**user 0.18 + sys 0.22 = 0.40s ≈ 单核 2%**。轮询间隔保持 1.5s 不变（不动 CableMonitor 的事件/生命周期代码，风险最小）。
  - 有意未做：`MonitorViewModel` 的 1Hz 功率采样按 UI 可见性降频——采样本身不做任何 IO（只读最近一次快照），优化后占比已极小，而停采会让功率曲线出现空洞（重新打开窗口时历史是断的），收益不抵体验损失。

- ✅ 视图层纯函数补测：`ViewFormattingTests` 覆盖 `prettyAdapterDescription`（缩写大写/词首大写）、`BatteryGlyph.symbol`（五档边界）、吞吐文案、`partnerVIDLabel`（厂商目录命中/未命中）。相关函数按仓库既有惯例改为 internal 并标注"internal 便于单测"。

- 测试总数：221 → 241（`CableKitTests` 162→168，`CableScopeAppTests` 16→30）。

## 三、真机踩坑记录（实现时必读，详见 Docs/03）

1. IOPort 节点 `IORegistryEntryGetChildEntry` 返回成功但空迭代器 → 用 `IORegistryEntryCreateIterator` + `kIORegistryIterateRecursively`。
2. `PowerSourceOptions` 是 CFSet（__NSCFSet）不是数组 → `as? NSSet` 桥接，按电压排序展示。
3. VDO Data 是线上小端序 → `UInt32(littleEndian:)`，已与 Apple 平铺字段交叉验证。
4. 内置根 hub 无 `LocationID`/`Speed` 属性 → 路径末段 `@hex` 回退。
5. `IORegistryEntryGetName` 不含 `@N` 位置段 → 端口 ID 用 `IORegistryEntryGetPath` 末段。
6. 端口节点上的 `SOPMfgString`（"Realtek"）是 HPM 控制器芯片厂商（RTBuddy），**不是**线缆 e-marker 厂商；e-marker 厂商看 SOP' 节点的 `Vendor ID`。

## 五、阻塞项集成设计与触发条件

### XID 认证核查（外部数据阻塞）

- **数据源**：USB-IF XID 认证清单，离线获取未果，待社区提供。
- **集成设计**：`usb-vendors.json` 条目扩展可选 `xid` 字段（如 `{"vid": "0BDA", "name": "Realtek", "xid": ["..."]}`）；`EMarkerSnapshot` 的 VID + productType 与清单匹配后，由 `EMarkerTrust` 新增 note case（如 `.certifiedMatch`）渲染"认证在册"提示——措辞仍守红线：**在册 ≠ 真伪判决**。
- **现状**：模型无 XID 字段；数据未到位前不引入无数据可测的死代码。

### dock 中间 hub 身份标注（部分顺延）

- 已落地（M6）：雷雳子树**深度缩进**（`depth`）。剩余：链路中间 hub 的身份标注（名称/端口）——system_profiler 不暴露中间 hub 的稳定标识，待找到可靠数据源。

### 线缆电阻估算（数据缺口，顺延）

- 估算需"合同电压 − 远端电压 = 压降"，而：远端（设备侧）电压 macOS 不暴露；顶层 `Amperage` 是**整机**抽流非端口值（多线时无法归属到线）；PPS/AVS 原始报文缺失（`PDOPortPowerSnapshot` 仅平铺档位）；电池侧微小放电会混入电流读数。
- **触发条件**：拿到端口级电流读数或远端电压感知数据（如雷雳坞站电压上报）后重启此项目。
