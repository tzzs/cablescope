# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, and other AGENTS.md-compatible tools) when working with code in this repository.

## What this is

CableScope: a macOS menu bar tool that inspects connected USB-C/Thunderbolt cables for charging speed, data transfer speed, video capability, and a derived cable rating. Requires macOS 14+ and Swift 5.10+ (Xcode 15+).

## Commands

```bash
swift build                              # build everything (CableKit, CLI, App)
swift test                               # run all test targets
swift test --filter PortGroupingTests    # run one test class
swift test --filter PortGroupingTests.testPortKeyKeepsBusAndRootPortNibble  # run one test method

swift run CableScopeCLI pretty           # human-readable snapshot
swift run CableScopeCLI snapshot --pretty
swift run CableScopeCLI watch            # --interval N sets fallback poll interval
swift run CableScopeCLI rating           # --reset clears persisted history
swift run CableScopeCLI properties [Class] [--json]   # dump raw IORegistry properties

swift run CableScopeApp                  # menu bar app, unbundled (no notifications)
./scripts/bundle_app.sh release && open build/CableScope.app   # bundle into a real .app

./scripts/check_layering.sh              # enforce the layering rule below (no IOKit/CoreGraphics/system_profiler outside CableKit)
```

There is also an Xcode project generated by `xcodegen` from `project.yml` (adds the `CableScopeWidget` desktop widget target, which is not in `Package.swift`). `CableScope.xcodeproj` is gitignored and regenerated with `xcodegen generate` — needed when working on the widget or App Store build config.

```bash
xcodegen generate                        # regenerate the Xcode project
xcodebuild -project CableScope.xcodeproj -scheme CableScopeWidget \
  -configuration Debug -destination 'platform=macOS' build CODE_SIGNING_ALLOWED=NO
```

CI runs exactly that (plus the App's `AppStore` configuration) after `swift test`, because `swift build` never compiles the widget: without it, a CableKit API change could break the widget and still merge green.

## Architecture: the layering rule

**All system access lives in `Sources/CableKit`.** `CableScopeCLI` and `CableScopeApp` consume only CableKit's value types (`Codable` + `Sendable` snapshots) — never IOKit, CoreGraphics, or `system_profiler` directly. New system reads belong in a CableKit service; the parsing logic must be isolated in a pure function so it can be unit-tested against captured real-device fixtures.

```
Sources/CableKit/
├── Models/       # Value-type snapshots: CableSnapshot, CableSession, CableRating, USBCPortSnapshot, ...
├── Services/     # One IOKit/system_profiler wrapper per protocol (ServiceProtocols.swift):
│                 #   USBService, PowerService, DisplayService, ThunderboltService,
│                 #   PortControllerService (AppleHPM/AppleTC), RegistryService (generic IORegistry dump)
├── Monitor/      # CableMonitor: composes all services into one CableSnapshot + change-event AsyncStream
├── Rating/       # CableRatingEngine (pure) + RatingStore (persistence) — historical-peak based rating
└── Diagnostics/  # Pure functions: charging bottleneck attribution, headline text, e-marker trust
Sources/CableScopeCLI/   # thin CLI on top of CableKit
Sources/CableScopeApp/   # SwiftUI menu bar app (MenuBarExtra + main window + Swift Charts) on top of CableKit
Sources/CableScopeWidget/  # desktop widget (WidgetKit), Xcode-project-only target
```

Consumers depend on the protocols in `Services/ServiceProtocols.swift`, not concrete service types, so tests can mock them.

### CableMonitor: hybrid event/poll model

`CableMonitor.snapshotNow()` fans out to all five services concurrently via `async let`; **a single service failing degrades to an empty array/nil for that field, it never fails the whole snapshot**.

`CableMonitor.snapshotStream()` yields an initial snapshot immediately, then re-samples on "event signal OR pollInterval timeout, whichever comes first" (default poll interval 1.5s). Three IOKit notification sources feed the same `DispatchSemaphore`: `AppleSmartBattery` interest notification (near-zero-latency power/charge changes), and USB device publish/terminate matching notifications (plug/unplug). Anything not covered by these (e.g. display/Thunderbolt topology changes) falls back to the poll interval. Content-signature deduplication (excluding id/timestamp) means only real changes get yielded. See the doc comment at the top of `Sources/CableKit/Monitor/CableMonitor.swift` for the full lifecycle/ownership rationale (why `DispatchSemaphore` over `AsyncStream` racing, notification port teardown order, etc.) before touching this file.

### system_profiler cost and the `TTLCache`

`DisplayService` and `ThunderboltService` are the only services that shell out to `system_profiler` (measured: ~0.15s for `SPDisplaysDataType`, ~0.05s for `SPThunderboltDataType`). Because `CableMonitor` re-samples every poll interval, running them unconditionally cost ~15% of a core continuously in a 24/7 menu bar app. Both now wrap that call in `Services/TTLCache.swift` — "cheap change probe + TTL ceiling":

- `DisplayService` keys the cache on the **online display ID set** (`CGGetOnlineDisplayList`, no subprocess), so plugging/unplugging a display invalidates it instantly; the 30s TTL is only a ceiling for changes the key can't see (e.g. a resolution switch altering the DP link rate).
- `ThunderboltService` has no equally cheap, verified change probe, so its key is constant and it degrades to pure TTL (5s) — a newly attached Thunderbolt device can take up to one TTL to appear.

Measured effect: `CableScopeCLI watch` over 20s went from 3.15s to 0.40s of CPU (including subprocesses). **If you add another `system_profiler`-backed read, give it the same treatment**, and keep the parsing pure/fixture-tested as usual.

### Multi-cable sessions (`PortGrouping.swift`)

Physical cables are inferred, not directly enumerable, so devices/ports are grouped into per-cable "sessions":

- USB devices: `portKey = locationID >> 20` (bus + first-level port bits of the 32-bit USB LocationID) groups a root port and everything hubbed off it into one session — this is what survives across external hubs/docks.
- Port-controller data (AppleHPM), when available, is the first-class session source: every `ConnectionActive = Yes` port becomes a card on its own, because a pure PD charging cable enumerates no USB/Thunderbolt device at all — the port session is the *only* way such a cable becomes visible.
- Thunderbolt devices key off `system_profiler`'s `receptacle_N_tag` and form independent sessions (no reliable port-node correlation yet).
- Charging power/5A-contract attribution follows `PortGrouping.attributablePowerSessionID`: unambiguous with exactly one cable; with multiple cables, attributed only when exactly one active port is the one actually receiving power, otherwise it lands in the catch-all `"sys"` bucket. Displays always land in `"sys"` (v1 has no display→port mapping).

### Rating engine (`Rating/CableRatingEngine.swift`)

Pure Swift, no IOKit dependency, fully unit-testable. Rates a cable from **historical negotiation peaks**, bucketed per session id (`"usb-0x014"`, port-controller node id, or `"tb-2"`) — peaks only ever increase, they never reset on unplug. Key inference rule: a PD contract negotiating ≥ 20V/5A implies a 5A e-marker chip. Full bucketing/attribution rules are documented in `Docs/03-数据获取指南.md` and in the file's header comment; read both before changing bucket semantics.

### Widget ↔ App preference sharing (`SharedAppPreferences`)

The widget is a separate process with its own bundle ID, so its `UserDefaults.standard` cannot see the app's language/theme settings — it used to just follow the system. `CableKit/Preferences/SharedAppPreferences.swift` is the shared contract: it owns the preference keys and the raw-value → `Locale`/`Appearance` mappings, opens the app's own preferences domain by bundle ID, and returns nil ("follow the system") whenever it can't read it.

No App Group is needed: on the external (Developer ID) channel neither target is sandboxed, and an unsandboxed process may read any preferences domain. **A sandboxed MAS build can't**, and degrades to following the system — exactly the pre-existing behavior. `AppPreferences` (App) delegates to the same constants and mappings so the two sides can't drift; `AppPreferencesTests` guards that with explicit assertions.

## Localization: classic `.strings` only, never `.xcstrings`

All three modules ship their English table as a hand-maintained `Resources/en.lproj/Localizable.strings`, with the Chinese source string as the key:

- `Sources/CableKit/Resources/en.lproj/Localizable.strings` (looked up by `KitLocalization`, explicit `locale:` parameter)
- `Sources/CableScopeApp/Resources/en.lproj/Localizable.strings` (SwiftUI `Text`/`LocalizedStringKey` via `Bundle.main` after `bundle_app.sh` flattens it, plus `AppLocalization` for AppKit-layer code)
- `Sources/CableScopeWidget/Resources/en.lproj/Localizable.strings` (the widget's own chrome; it is a separate bundle, so the App's table does not cover it. Headline text comes from CableKit instead — both are driven by the locale `SharedAppPreferences` resolves)

**Do not reintroduce `.xcstrings`.** The classic SwiftPM build engine (what CI and the release workflow use) does not compile String Catalogs — it copies the raw JSON, so `en.lproj` never exists, every English lookup silently falls back to the Chinese key, and `bundle_app.sh`'s lproj-flattening step skips silently without failing the build. This bit CableKit (5401f72) and then the App layer (whose entire English UI was affected in release builds until it was migrated too). `AppLocalizationTests` / `DiagnosticsTests` assert real English output so a regression fails CI instead of shipping.

Two further traps, both already fixed but easy to reintroduce:

- When resolving the resource bundle, probe the nested `CableScope_*.bundle` **first** and only fall back to `Bundle.main` — under `swift test`, `Bundle.main` is the xctest runner, which has its own `en.lproj` and will happily answer every lookup with the key itself.
- A `String` interpolated into a `LocalizedStringKey` (e.g. `"写入 \(speedText(...))"`) is substituted as `%@` and **is not looked up again**. Any Chinese fallback text inside such a value must be localized explicitly via `AppLocalization`/`KitLocalization`.

## Wording red lines (from CONTRIBUTING.md — enforced in review)

These exist so the tool never claims to know more than it actually read from hardware:

- **Never output a "fake/counterfeit cable" verdict.** If e-marker data looks unusual (zero VID, reserved bit values, unlisted VID), describe what was read ("VID not reported", "unusual value") — never label a cable fake or non-compliant.
- **Capability claims not read directly from hardware must use lower-bound phrasing** ("supports at least …" / "may …"). Inferred ratings are inferences from negotiation peaks, never certificates.

## Testing conventions

Three test targets live in `Tests/`, all required to pass on any machine (including CI's empty runner):

- **Fixture tests** (`Tests/CableKitTests`) parse captured real-device IORegistry samples (e.g. `PortParsingTests`, `PowerParsingTests`) — deterministic regardless of what's plugged in. **New parsing logic must ship with a fixture test built from a real-device sample**; if you couldn't capture one, say so explicitly.
- **Smoke tests** (`RealEnvironmentSmokeTests`, also in `CableKitTests`) call the real services directly and must not assume any specific hardware is present — they exercise the "no device/no data" degrade path. `RegistryServiceTests` follows the same rule for the generic IORegistry inspector, with a handful of fully deterministic cases (empty/unknown class name) that need no hardware at all.
- **App-layer tests** (`Tests/CableScopeAppTests`, `@testable import CableScopeApp`) cover the pure logic that lives above CableKit: `UpdateChecker`'s semantic-version comparison, `AppPreferences`'s notification-gating rules (each test backs up/restores the `UserDefaults.standard` keys it touches), view-layer formatting helpers (`ViewFormattingTests`), English localization (`AppLocalizationTests` — see the localization section below), and a `MonitorViewModel` smoke test using a real `CableMonitor` with an injected `ratingsURL` (a temp file) so it never touches the user's real `~/Library/Application Support/CableScope/ratings.json`.

Localization and resource-bundle behavior differs between SwiftPM build engines, and CI uses the classic one. When touching resources or localization, verify with **both**: `swift test` and `swift test --build-system native --scratch-path /tmp/native-check`.

## Release process

Two independent GitHub Actions workflows cover the release path:

- **[release-please.yml](.github/workflows/release-please.yml)** (push to `main`) maintains a standing "release PR" from Conventional Commits history (`release-please-config.json` + `.release-please-manifest.json`, `release-type: simple`). Merging that PR bumps `CHANGELOG.md` + the manifest, creates the GitHub Release, and pushes the `vX.Y.Z` tag that triggers the build/publish workflow below.
- **[release.yml](.github/workflows/release.yml)** — named **Publish**, not "Release", so it is not confused with "Release Please" in the Actions list. The *file* keeps its `release.yml` name on purpose: GitHub tracks a workflow's run history by file path, so renaming it would orphan every past run. Trigger it by file name (`gh workflow run release.yml -f tag=v0.2.0`) or by display name (`gh workflow run Publish -f tag=v0.2.0`). On push of a `v*` tag it builds, signs, notarizes, uploads the DMG + CLI binary onto the Release that release-please already created, and syncs the Homebrew tap. It never creates the Release itself.

  It also accepts a **`workflow_dispatch` with a `tag` input**, which exists because of a trap worth internalizing: **a tag-triggered workflow runs the workflow file as of the tagged commit.** Fixing a bug in `release.yml` therefore does nothing for tags that already exist — release-please tags the *release PR's merge commit*, which predates any fix merged afterwards. That is exactly how v0.2.0 ended up a published-but-empty Release: the fix was on `main`, the tag pointed one commit behind it, and the old `gh release create` hit "a release with the same tag name already exists". Dispatching manually takes the workflow from the default branch and the source from the given tag, so a botched or superseded release can be re-published without ever moving or re-cutting a tag.

  Two guards make that safe, and both matter: a manual dispatch **skips the Homebrew tap sync unless the given tag is the latest release** (syncing the tap to an older tag would downgrade every user), and the tap step **skips any template the checked-out tag does not carry** (an old tag predates templates added later — `cablescope-cli.rb` does not exist at `v0.2.0`, and an unguarded `cp` under `set -e` would fail the job *after* the assets had already been uploaded).

**Two release-please config settings are load-bearing — do not change them without reading this.**

- **`skip-github-release` must stay off.** release-please creates the tag *as part of* creating the GitHub Release; turning that flag on suppresses both. The release PR then merges into a "merged but untagged" state, `release.yml` never fires, and — worse — every later push aborts with `There are untagged, merged release PRs outstanding`, so no new release PR is ever opened again. The job still reports success, so nothing alerts you. (This is exactly how the 0.2.0 release got stuck.) Recovering from that state means creating the missing tag/Release by hand and relabeling the merged release PR from `autorelease: pending` to `autorelease: tagged`.
- **`include-component-in-tag: false` must stay set.** With `package-name: CableScope` and component-in-tag left at its default, tags come out as `CableScope-vX.Y.Z`, which matches neither `release.yml`'s `on: push: tags: v*` filter nor its `VERSION="${GITHUB_REF_NAME#v}"` version derivation.

`release.yml` uploads onto the existing Release rather than creating it (`gh release create` would fail on an already-existing one), falling back to creating it only when a tag was pushed by hand.

**`RELEASE_PLEASE_TOKEN` is required, not optional.** release-please pushes commits/tags using this token; if it fell back to the default `GITHUB_TOKEN`, the resulting tag push would silently *not* trigger `release.yml` (GitHub Actions' recursive-trigger protection blocks workflows from triggering other workflows when they run under `GITHUB_TOKEN`) — a release PR would merge, look successful, and never actually publish anything. `release-please.yml` therefore fails the job explicitly (`::error::` + `exit 1`) when the secret is missing, instead of skipping. This is intentionally different from `release.yml`'s other secrets (signing cert, notarization credentials, `HOMEBREW_TAP_TOKEN`), which stay skip-when-missing by design so unsigned/unnotarized releases still work without a full Apple developer setup. Two consequences are enforced in the workflow: **an unnotarized DMG is never synced to the Homebrew tap** (a cask install of an unnotarized app is blocked by Gatekeeper, so the tap stays on the last installable version while the DMG still ships on the GitHub Release), and **an unnotarized Release gets a notice appended to its body** telling users they must allow the app under System Settings → Privacy & Security, or install the CLI formula instead. The notice is idempotent — it is keyed off an HTML-comment marker so manual re-publishes do not stack duplicates. Never remove that notice to make a release look cleaner: shipping an unnotarized build silently is the thing it exists to prevent.

## Homebrew distribution

CableScope ships as **two independent packages**, because the app and the CLI have different trust models — a cask distributes a pre-built binary (Gatekeeper applies quarantine, so it must be notarized), while a formula builds from source on the user's machine (no signing involved at all).

| | `Casks/cablescope.rb` | `Formula/cablescope-cli.rb` |
| --- | --- | --- |
| Product | `CableScope.app` → `/Applications` | `cablescope` command → `bin` |
| Source | notarized DMG from the GitHub Release | source tarball of the tag, built locally |
| Needs Apple Developer secrets | **yes** | no |
| Synced by `release.yml` | only when notarization succeeded | always |

Templates live in `Packaging/homebrew/`; `release.yml` copies them into `tzzs/homebrew-tap`, substituting the version/URL and hashes. **Three names are deliberately different and none of them should be "unified":** package token `cablescope-cli` (must not collide with the cask's `cablescope` token inside one tap — Homebrew only gives core-tap formulae the "formula wins" shortcut, third-party taps stay ambiguous), command name `cablescope` (short to type), SwiftPM target `CableScopeCLI` (a source-level identifier that should never appear in a user's install command).

**The formula must install the executable and `CableScope_CableKit.bundle` into the same directory (`libexec`), never `bin` directly.** CableKit's resources (`usb-vendors.json`, the English `.strings`) live in that separate bundle, and when the binary is invoked through Homebrew's symlink in `bin`, `Bundle.main` does *not* resolve the symlink — it reports `bin/`. Of `CableKitResourceBundle.probe()`'s four candidates, only #2 (`Bundle(for:).resourceURL`, which goes through the dyld image path and *does* resolve) lands on `libexec/`. Verified empirically:

```
❌  1 main.resourceURL            → .../bin/CableScope_CableKit.bundle
✅  2 Bundle(for:).resourceURL    → .../libexec/CableScope_CableKit.bundle
❌  3 main.bundleURL              → .../bin/CableScope_CableKit.bundle
❌  4 Bundle(for:).bundleURL/..   → .../CableScope_CableKit.bundle
```

Lint both templates with Homebrew's own linter before changing them:

```bash
brew style Packaging/homebrew/cablescope-cli.rb Packaging/homebrew/cablescope.rb
```

`Style/FrozenStringLiteralComment` is a known false positive here and should be ignored — it fires only because these files live in `Packaging/homebrew/` instead of a tap's `Formula/`/`Casks/` directory; real tap formulae carry no such comment. Everything else it reports is real.

That candidate was originally added for a `swift test` toolchain quirk and only incidentally covers the Homebrew layout. Trimming the candidate list as "redundant" would silently degrade brew-installed CLIs — no vendor names, English UI falling back to Chinese — **without any error**, since `probe()` is designed to return nil rather than fail. The formula's `test do` block cannot catch this either (see the note in the file).


## PR/change checklist

- No IOKit / CoreGraphics / `system_profiler` calls outside `CableKit` (the layering rule above) — `./scripts/check_layering.sh` enforces this in CI; run it locally before pushing if you touched `CableScopeCLI`/`CableScopeApp`/`CableScopeWidget`.
- `usb-vendors.json` (VID → vendor name database): one record per real, assigned VID, with a `source` field (e.g. `usb.ids`) — never a placeholder/guessed entry.
- **Keep `README.md` and `README.zh-CN.md` in sync** — same information, mirrored in both languages. Update `Docs/` when behavior or data sources change.

## Commit messages

Follow [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <description>`.

- **Types used in this repo**: `feat`, `fix`, `docs`, `test`, `build`, `chore` (add `refactor`/`perf` when applicable).
- **Scope** is the affected area, e.g. `kit`, `app`, `cli`, `widget`, `design`, `roadmap` — omit it only for changes that cut across all of them.
- The description is written in Chinese, matching existing history (e.g. `feat(kit): USB-C 端口控制器直读数据层 + 充电诊断 + 评级存储统一`).
- A breaking change adds `!` after the type/scope (`feat(kit)!: ...`) and/or a `BREAKING CHANGE:` footer.
